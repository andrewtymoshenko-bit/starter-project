## 2. Змінений маршрут

Основний змінений маршрут – пошук інцидентів:

1. Користувач відкриває URL пошуку в браузері або надсилає запит із HTTP-файла: `GET /api/incidents/search?q=USB`.
2. У `Program.cs` виклик `app.MapLab02Endpoints()` реєструє маршрути scaffold. Обробник пошуку розташований у `src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs`.
3. Сервер читає `q` і `sortBy`. Невідоме сортування відхиляється з `400` до запиту до БД. Для значення пошуку екрануються спеціальні символи ILIKE.
4. Через `SecureLabDbContext` формується LINQ-запит до Incidents. Він шукає підрядок у Title або Description:

   ```csharp
   EF.Functions.ILike(incident.Title, pattern, "\\")
       || EF.Functions.ILike(incident.Description, pattern, "\\")
   ```

5. Провайдер EF Core/Npgsql перекладає LINQ у SQL і передає pattern окремим параметром. Сортування обирається через дозволені LINQ-вирази; клієнтський текст не підставляється в ORDER BY.
6. `ToListAsync(ct)` виконує запит у PostgreSQL. Сервер повертає JSON із полями Id, Title, Description, Severity, Status і CreatedAtUtc. Браузер відображає відповідь.

Другий маршрут – `POST /api/incidents`: JSON → `CreateIncidentRequest` → серверна валідація → перевірка конфлікту через `AnyAsync` → створення entity → `SaveChangesAsync` → `201 Created` із `CreatedIncidentResponse`. Помилки контракту повертають `400`, предметний конфлікт – `409`.

Для перевірок використано `tests/http/lab-02-checks.http`, успадкований scaffold-сценарій `tests/http/lab-02-search.http`, тести `IncidentCreateTest.cs` і `IncidentSearchTests.cs`. Початкові дані відновлює `DatabaseBootstrap.cs`

## 3. Виконані зміни

**Контракт створення.** Request DTO приймає тільки Title, Description, Severity та OccurredAtUtc. Ідентифікатор, власник, status і службові часи встановлює сервер. Response DTO відокремлено від entity; внутрішні зв'язки й власник не передаються у відповідь.

| Правило | Реалізація | Відповідь за порушення |
|---|---|---|
| Назва | Не порожня після Trim; довжина вхідного значення до Trim ≤ 160 | 400, errors.title |
| Опис | Не порожній після Trim; довжина вхідного значення до Trim ≤ 4000 | 400, errors.description |
| Severity | Enum.TryParse без урахування регістру та Enum.IsDefined: Low, Medium, High, Critical | 400, errors.severity |
| Дата | Обов'язкова; не пізніше UTC-часу сервера на початку обробки плюс 5 хвилин | 400, errors.occurredAtUtc |
| High/Critical | Опис після Trim має не менше 40 символів | 400, errors.description |
| Повторна назва | Та сама назва після Trim у тому самому регістрі вже існує у New, Triaged, InProgress або Resolved | 409, Problem Details |

Статус Closed не блокує повторне створення. Перед збереженням дата переводиться в UTC через `ToUniversalTime()`. Валідація полів і cross-field перевірка виконуються до доступу до БД.

**Пошук.** SQL-конкатенацію та `FromSqlRaw(sql)` замінено LINQ із параметризованим ILike. Щоб отримати буквальний пошук підрядка, спочатку екранується `\`, потім `%` і `_`; зовнішні `%` додає сервер. Апостроф не видаляється.

**Сортування.** Allowlist містить `createdAtUtc`, `severity`, `status`. Відсутнє або порожнє значення означає `createdAtUtc`; невідоме – `400`, ключ sortBy. CreatedAtUtc сортується за спаданням. Для enum зі строковим зберіганням використано явні ранги: Critical → High → Medium → Low та New → Triaged → InProgress → Resolved → Closed. `ThenBy(Id)` визначає порядок при рівності основного значення; вибірку обмежено 50 записами.

**Тести.** Додано вісім автоматичних негативних сценаріїв створення, перевірку повторної назви й чотири перевірки буквального пошуку `%`, `_`, `\` та апострофа. Тести створення контролюють Problem Details і відсутність небажаних записів. Тести пошуку перевіряють точну множину Id: спільний префікс знаходить обидва створені записи, повний текст зі спеціальним символом – тільки потрібний. Власні тестові записи видаляються у finally.

## 5. Security-сценарій

**Гіпотеза.** Якщо недовірений q склеюється з SQL-текстом, він може змінити умову пошуку; якщо sortBy без перевірки використовується в ORDER BY, клієнт впливає на структуру запиту.

**Стан «до».** На commit `338617c0839f263eac043740f7981a135c9f22a6` метод `MapLab02Endpoints` у `Scaffolding/Lab02Endpoints.cs` складав SQL із q і sortBy та виконував його через FromSqlRaw.

**Мінімальний локальний PoC.** На локальному стенді з п'ятьма seed-записами виконано контрольний read-only запит C із `tests/http/lab-02-checks.http`. Точний запит збережено в цьому HTTP-файлі. Він містив завершення строкового літерала, істинну умову та коментар. 

**Спостереження.** A (USB) повернув один запис, B (відсутній текст) – порожній масив, C – усі п'ять початкових записів. D (O'Brien) викликав 500 із Problem Details. 

**Першопричина.** Значення q ставало частиною SQL-команди до виконання. Апостроф завершував строковий літерал, додаткова умова змінювала логіку, коментар відсікав решту тексту. Звичайний апостроф у D ламав синтаксис. Проблема полягає у змішуванні даних зі структурою SQL.

**Виправлення.** На commit `b1395bd7becb7d0fe91fda4f1b480a9ac664b99a` застосовано параметризований LINQ/ILike для введення, escaping для буквальної семантики wildcard і allowlist для структури сортування. SQL-конкатенацію прибрано. Параметризація й escaping виконують різні задачі: перша відокремлює дані від SQL-інструкцій, друге робить спеціальні символи ILIKE буквальними.

**Повторна перевірка та позитивна регресія.** Той самий C після виправлення повернув 200 і []; B також повернув []. A зберіг правильний результат, D повернув 200 й один O'Brien classroom report. Невідоме sortBy відхиляється з 400. Чотири автоматичні перевірки підтвердили буквальний пошук спеціальних символів. 

## 6. Висновок

У роботі реалізовано серверну валідацію створення інцидентів, cross-field правило для High/Critical, конфлікт повторної назви та окремий response DTO. Некоректні запити повертають 400, конфлікт – 409, відсутній інцидент – 404.

На локальних штучних даних відтворено SQL injection і пояснено його першопричину. Після переходу на параметризований LINQ контрольне введення більше не розширює вибірку, а звичайний пошук з апострофом працює. Перевірено allowlist сортування й буквальну семантику спеціальних символів. Збірка, автоматичні тести та зазначені ручні перевірки успішні. Вразливий і виправлений стани збережено окремими commits; розширення ЛР 1 збережено.
