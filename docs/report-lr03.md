## 2. Змінений маршрут

Основний змінений маршрут — автентифіковане створення інциденту з визначенням власника на сервері.

1. Користувач вводить дані у форму входу в `Client/auth-lab.html`.
2. Обробник у `Client/auth-lab.js` надсилає `POST /api/auth/login`. Middleware перевіряє ліміт запитів.
3. Обробник у `Scaffolding/Lab03Identity.cs` викликає `SignInManager.PasswordSignInAsync()`. ASP.NET Core Identity перевіряє пароль через штатний verifier і EF stores у PostgreSQL.
4. Після успіху сервер повертає `204` та встановлює захищену cookie автентифікації. Браузер надсилає її з наступними запитами до цього сайту.
5. Authentication handler перевіряє cookie та формує `HttpContext.User`. Запит `GET /api/me` отримує поточного користувача за `ClaimTypes.NameIdentifier` і повертає безпечний `CurrentUserResponse`.
6. Форма створення надсилає `POST /api/incidents` із title, description, severity та occurredAtUtc, без поля власника.
7. Захищений обробник у `Scaffolding/Lab02Endpoints.cs` перевіряє дані й бере GUID власника з principal. `SecureLabDbContext` зберігає інцидент у таблиці `incidents` PostgreSQL із цим `OwnerUserId`.
8. Сервер повертає `201` та безпечний response DTO. JavaScript показує відповідь через `textContent`.

Ключовий фрагмент визначення власника:

```csharp
var userIdClaim = httpContext.User.FindFirstValue(ClaimTypes.NameIdentifier);
if (!Guid.TryParse(userIdClaim, out var ownerId))
    return Results.Unauthorized();
// Під час створення сутності: OwnerUserId = ownerId.
```

Ключові файли: `Program.cs`, `Scaffolding/Lab03Identity.cs`, `Scaffolding/Lab02Endpoints.cs`, `Client/auth-lab.html`, `Client/auth-lab.js`; надані Identity-модель і `SecureLabDbContext` використовуються без паралельного сховища користувачів чи власної криптографії.

## 3. Виконані зміни

1. **Реєстрація.** Додано перевірки обов’язковості, довжини та формату username, email і displayName. Пароль перевіряє Identity: мінімум 10 символів зі стандартними вимогами до цифри, великих і малих літер та неалфавітно-цифрового символу. Політику scaffold не послаблено.
2. **Безпечні відповіді.** Уведено `RegistrationResponse` і `CurrentUserResponse` із полями `id`, `userName`, `displayName`. Успішна реєстрація повертає `201`. Duplicate username/email повертає `409`; інші відмови реєстрації — `400` із безпечним повідомленням.
3. **Профіль.** `/api/me` вимагає автентифікації й читає id лише з перевіреного principal. Довіру до `X-Demo-UserId` усунено. Для відповіді профілю встановлено `Cache-Control: no-store`.
4. **Вихід.** Заглушку logout замінено викликом `SignInManager.SignOutAsync()`. Маршрут захищено; успішний вихід повертає `204`.
5. **Створення інциденту.** `POST /api/incidents` захищено через `RequireAuthorization()`. Власник визначається з principal замість фіксованого Alice. Зайве поле `ownerUserId` ігнорується JSON-десеріалізацією, бо його немає в request DTO.
6. **Браузер.** Реалізовано register → login → profile → create → logout. Стан сеансу визначається запитом `/api/me`: authenticated, anonymous або unknown при неможливості перевірки. Профіль очищається після виходу; створення доступне лише у стані authenticated. Значення паролів очищаються після запитів. Облікові дані та профіль не записуються в Local Storage / Session Storage.
7. **Cookie.** Збережено надані налаштування Identity; додано тест фактичних атрибутів cookie після входу через HTTPS тестового сервера.
8. **Rate limit.** До login застосовано fixed window: 10 запитів за 60 секунд на IP, `QueueLimit = 0`, після перевищення — `429 Problem Details`. Параметри читаються з конфігурації запущеного застосунку. Для ізольованого тесту задано 2 запити за 3 секунди та перевірено відновлення.
9. **Журнали.** Додано події `login/success`, `login/failed`, `login/rate_limited` і `logout/success`. Поля: `AuthEvent`, `Outcome`, `TraceId`.
10. **Регресія.** Старі `IncidentCreateTests` і `IncidentSearchTests` переведено на автентифікований клієнт зі збереженням перевірок ЛР №2. Додано `RegistrationTests`, `AuthenticationTests`, `IncidentOwnershipTests`, `CookieSecurityTests` і `LoginRateLimitTests`.

### Cookie, строк дії та межа локального HTTP

У `ConfigureApplicationCookie`: `HttpOnly = true`, `SameSite = Lax`; для Development — `SecurePolicy = SameAsRequest`, для інших середовищ — `Always`. HttpOnly обмежує читання cookie JavaScript; Secure обмежує передавання HTTPS; SameSite обмежує частину міжсайтових запитів.

На локальному HTTP прапорець Secure може бути відсутній за політикою SameAsRequest. Тому браузерний HTTP-сеанс не є доказом Secure: його наявність перевірено окремим HTTPS-тестом. Також перевірено HttpOnly, SameSite=Lax та Path=/.

Вхід використовує `isPersistent: false`: cookie є сеансовою й не має Expires/Max-Age. Стандартний строк authentication ticket — 14 днів, із sliding expiration; ці defaults у роботі не змінено. Строк ticket відрізняється від строку зберігання cookie. Закриття браузера не виконує logout, а браузер може відновлювати сеансові cookie. SignOutAsync прибирає cookie поточного клієнта, але не гарантує негайного відкликання скопійованого ticket чи сеансів інших пристроїв.

### Обґрунтування ключа обмеження та полів подій

Ключ — `RemoteIpAddress` серверного з’єднання. Зміна username не створює новий ліміт для тієї самої адреси. У поточній конфігурації клієнтський `X-Forwarded-For` не використовується як довірене джерело IP; спробу обходу таким заголовком перевірено тестом.

Компроміси: користувачі за NAT ділять квоту; розподілені спроби з різних IP можуть її обходити. Ліміт враховує всі запити входу, зокрема успішні. Він зберігається в пам’яті одного процесу, не забезпечує спільної квоти для кількох серверів і скидається при перезапуску.

Із власних auth-подій навмисно виключено username, email, пароль, password hash, security stamp, cookie, token і request body. TraceId дає змогу зіставляти події конкретного запиту без запису credentials.

## 5. Security-сценарій

**Гіпотеза.** Якщо сервер визначає особу за клієнтським `X-Demo-UserId`, можна отримати чужий профіль без підтвердження його власника. Якщо create не вимагає входу та використовує фіксованого Alice, інцидент не прив’язується до verified користувача, який виконав операцію.

**Стан до.** У scaffold `/api/me` читав GUID із `X-Demo-UserId`; без заголовка повертав 501. Logout був заглушкою 501. Create успадковував фіксованого власника Alice та не вимагав автентифікації. Початковий браузерний запуск після входу Alice показав 204 / 501 / 501 для login / me / logout.

**Мінімальний локальний PoC.** Для перевірки довіри до клієнтського id достатньо запиту до локального `/api/me` із `X-Demo-UserId` іншого навчального користувача. Для create — виконання від імені Bob із доданим ownerUserId Alice. Окремий успішний запуск підробленого заголовка у вразливому стані не зафіксовано: хибну довіру встановлено переглядом scaffold, а початкову заглушку — браузерним запуском. Це розмежовує аналіз коду й фактичний HTTP-доказ.

**Першопричина.** Дані клієнта перетинали межу довіри як доказ особи; create не використовував автентифікований principal. Відомий GUID не є підтвердженням входу.

**Виправлення.** `/api/me` і create захищено RequireAuthorization. Id отримується з ClaimTypes.NameIdentifier перевіреного principal. У create DTO немає ownerUserId; незнайоме поле не впливає на сутність. Реалізовано штатний sign-out Identity.

**Повторна перевірка.** A-03 підтверджує, що cookie Bob із заголовком Alice повертає незмінний профіль Bob. A-05 підтверджує 201 та фактичного власника Bob у новому записі бази попри ownerUserId Alice. A-01 підтверджує 401 без входу. A-06 підтверджує 401 після logout тим самим клієнтом.

**Позитивна регресія.** Bob успішно отримує власний профіль (A-02) і створює інцидент без owner у DTO (A-04). Власні браузерні сценарії працюють; попередні перевірки валідації, duplicate і пошуку ЛР №2 збережено.

**Залишкові ризики та компроміси.**

- Повної CSRF-моделі ще немає: це навчальний борг до ЛР №6. SameSite=Lax зменшує частину ризику, але не замінює CSRF-захист. HttpOnly і CORS самі по собі його не усувають.
- `/api/auth/register` розкриває зайнятість username/email через 409. Це прийнятий компроміс узгодженого duplicate-контракту; обмеження login не поширюється на register.
- `/api/auth/login` повертає однакові 401 для unknown user і wrong password, проте тест не доводить відсутності часових відмінностей. Rate limit зменшує частоту спроб, але не усуває всі канали перебору.
- Визначення owner із principal забезпечує правильне призначення власника при створенні. Це не є реалізацією повної авторизації читання чи зміни будь-якого інциденту.
- Локальний HTTP не забезпечує шифрування транспорту. Успішний HTTPS-тест flags перевіряє cookie-контракт, а не захищеність усієї локальної мережі.
- Cookie, необхідна в authentication-заголовках і браузерному cookie-сховищі, не повинна копіюватися у JSON-відповіді, журнали, Git чи докази.

## 6. Висновок

Виконано ЛР №3 на обраному рівні «Добре»: завершено реєстрацію на ASP.NET Core Identity, профіль із verified principal, захищене створення інциденту з серверним визначенням власника та logout. Реалізовано власний браузерний сценарій, обмеження запитів входу й мінімальні журнали подій без credentials.

Автоматизовано A-01–A-07, duplicate, фактичні cookie flags і rate limit із відновленням. Після помилки тесту rate limit виправлено раннє читання конфігурації; повторний тест і повний набір пройшли успішно за повідомленими результатами. Ручні браузерні перевірки підтвердили стан сеансу, створення після входу, очищення профілю після виходу та відсутність облікових даних у Local/Session Storage.

Задокументовано межу довіри, стандартну перевірку пароля, обмеження cookie й локального HTTP, канали перебору акаунтів та залишковий CSRF-ризик. Фінальні Git-артефакти оформлюються після збереження звіту й завершальної перевірки.
